Native Shell（NSH）在 iOS、Android、macOS、Windows、Linux 和 Web 上提供原生视图与交互，界面长什么样由应用自己决定。同一套组件模型既能写完整应用，也能嵌进现有应用，还能在运行时下发界面。

## 原生打底，设计归应用

NSH 用的是各平台自己的视图、文本和输入能力，并按设备适配交互：键盘导航、鼠标与触摸、文本编辑、滚动和无障碍（[简介](./index.md#native-的含义)）。

颜色、字体、间距、形状、状态反馈和动画都由应用定义。比如设置页在 iOS 和 Android 上可以保持品牌风格，输入和导航仍然符合各设备的习惯。设计师通过样式和组件部件调整外观。

原生视图是渲染的底座；系统风格控件只是一种可选的外观和行为，不是必须。NSH 的通用控件提供共享行为和可定制部件，方便你搭建自己的设计系统。

## 原生集成具体指什么

原生底座包括渲染、按帧驱动的动画、输入和无障碍。

在 iOS 和 Android 上，[Input](../elements/input.md) 直接用平台的文本输入框。编辑、选择菜单、输入法和平台支持的自动填充都交给系统。你用 `autoComplete` 说明字段用途，比如 `current-password` 或 `postal-code`，系统再根据设置和服务给出建议（[表单与键盘](./forms-and-keyboard.md)）。改输入框样式不会丢掉这些系统能力。

自绘渲染器要自己画输入框，也得自己对接系统编辑和无障碍服务。NSH 只要后端有平台文本控件就直接用。各后端的集成范围见各自文档，其中 Windows 和 GPUI 嵌入后端用的是 NSH 自己的编辑器（[平台](./platforms.md)）。

NSH 的分层借鉴了 [GPUI Kit](https://gpui-kit.com)：组件行为和视觉设计分开。NSH 在这之上再接入平台视图和输入。

## 一套组件模型，跨所有平台

开关在手机、桌面和 Web 上含义相同。[`nsh/base`](../modules/nsh-base.md) 负责状态、输入处理、焦点和无障碍，应用负责 [Switch](../elements/switch.md) 的轨道、滑块和各状态的样式。按钮、复选框、单选框也一样。

| 职责 | 归属 | 示例 |
|---|---|---|
| 渲染、布局、响应式与环境 | `nsh-core`、`nsh` 及运行时模块 | 视图、文本、signal、样式 |
| 共享行为与无障碍结构 | `nsh-base`，TSX 中导入 `nsh/base` | `Button`、`Checkbox`、`Switch`、`Tabs` |
| 视觉设计与带样式的组件 | 应用或社区组件库 | 品牌控件、卡片、表单行 |
| 平台专属能力 | `nsh/mobile`、`nsh/desktop` | 移动导航栏、桌面窗口控制 |

通用控件统一放在 `nsh/base`。平台模块只放带平台语义的东西：

- [`TabBar`](../modules/nsh-mobile.md#tabbar) 是移动端顶层导航；[`Tabs`](../elements/tabs.md) 在所有平台切换标签内容。两者用途不同。
- `nsh/mobile` 只收交互方式为移动端特有的能力。
- 通用控件如果只是外观、尺寸、颜色或动画不同，放在共享组件和应用样式里处理。
- 通知、Toast 这类各平台用途相同的能力，先定一份跨平台契约，再由组件内部适配呈现。

共享组件可以在内部适配交互：菜单在桌面上弹出，在手机上以底部面板出现，应用只用一套 API，外观自己定。导航标题栏、系统提示框这类由系统管理的呈现，按文档里的平台规则走。想开放自己的原生组件和服务，用[嵌入接口](./native-components.md)。

## 无样式底座与组件库层

NSH 负责基础元素和无样式底座，即 `nsh-core` 和 `nsh-base`。带样式的组件库由应用或第三方提供，相当于 [GPUI Kit](https://gpui-kit.com) 里 `gpui-component` 的角色。这样每个产品都能掌控外观，又能复用组件里最难写的行为部分。

这个分工来自 [GPUI Kit](https://gpui-kit.com) 的经验。它的带样式组件起源于长桥 Longbridge Pro。应用的设计越来越多样，用户为了定制开始 fork 组件。把共享底座抽到 `gpui-base` 后，不同设计可以复用同一套行为。带样式组件仍然适合做设计参考，也适合定制需求不超出其能力的应用；其他应用则通过底座直接掌控呈现。

NSH 一开始就这样分：

- `nsh/base` 负责复杂行为、交互、响应式状态、焦点、无障碍和适配设备的呈现，每种行为在它所属的层测试。[Dock](../elements/dock.md) 这样的大型结构也在其中。
- 应用用样式、状态、插槽和部件在上面搭出自己的设计。
- 视觉默认值和品牌变体属于应用或第三方组件，贡献的组件也一样。
- 文档已约定的系统呈现和 `TextView` 阅读默认值，继续按各自契约执行（[架构](./architecture.md#三层结构)）。

### Gallery 展示的是什么

官网演示和 Gallery 是带样式的示例应用。里面的渐变、阴影、圆角、过渡和动效，用来展示 NSH 能定制到什么程度，源码也可以直接参考。这些样式属于演示本身，不属于基础组件；基础组件只提供下面的行为和部件。你可以照搬示例，也可以做完全不同的风格。

单独发布的带样式组件库属于上面说的应用与社区层。Gallery 只代表一种设计方向，适不适合你的产品，由你判断。

## Rust 与 TSX 共用一个引擎

纯 TSX 应用、用 Rust 扩展的 TSX 应用和纯 Rust 应用，共用同一套基础元素、基础组件、signal 和布局。

- **TSX** 写界面、状态和逻辑，迭代快，同样的模块还能在运行时下发。
- **Rust** 通过 [nshm](./nshm.md) 提供编译后的逻辑和可复用的原生组件，也可以写整个应用（[用 Rust 开发](./rust.md)）。

引擎只更新依赖已变化 signal 的绑定，并批量提交视图操作。文本布局、原生动画和输入由引擎及平台后端负责（[架构](./architecture.md)）。性能用可复现的应用负载来衡量（[性能](./performance.md)）。

## 嵌入、动态下发与 AI

已有原生应用可以在需要的位置放入 NSH 视图，并开放自己的原生组件和宿主服务。独立应用用的是同一套运行时和组件模型（[平台](./platforms.md)）。

动态下发的 TSX 模块自带状态、逻辑和布局。宿主决定两件事：

- **信任**：签名包决定宿主信任哪些发布者（[签名包](./signed-packages.md)）。
- **权限**：沙箱限制和能力配置决定模块能做什么（[沙箱与能力](./sandbox-and-capabilities.md)）。

AI 生成的界面走同样的流程：

1. 按已声明的 API 生成 TSX。
2. 检查并测试。
3. 构建并签名模块。
4. 按宿主策略验证后运行。

自动生成的类型声明、给模型读的文档和 CLI 测试，让这个流程可检查、可重复（[测试与追踪](./testing-and-trace.md)）。

## 按这些目标扩展 NSH

1. 先明确用户行为，以及它是否各平台通用。
2. 通用行为放进现有基础元素或基础组件，暴露状态和部件供应用定制。
3. 带平台语义的能力放进对应平台模块，写清适用范围和如何与共享 UI 组合。
4. 带样式的组件放在应用或社区组件库里做。
5. 在受影响的平台上验证行为、无障碍、布局和输入，并用中英文写好公共契约文档。

照这些原则，NSH 扩展时视觉设计保持灵活，共享 API 保持一致，平台集成边界保持清晰。
